SWEET COMMUNICATION / BANGKOK / SEPTEMBER 2025 TO FEBRUARY 2026

I built the infrastructure and supported it.

I took two existing computers, made them into Proxmox servers and built an open-source environment around the work the company needed to do. I also looked after the computers, accounts, support and documentation afterwards.

The environment supported 61 client computers. The budget was limited, and replacing every piece of equipment was not an option. I had to work with what was there, make it manageable and stop the same small problems from taking up the whole day.

This was a call-centre environment. A working computer was only one part of someone being able to work. The browser, headset, network connection, business tools and user access all needed attention. I needed a way to support those together.

01 / BUILDING THE ENVIRONMENT

Two Proxmox servers and the services around them

All hosted services ran in VMs across the two Proxmox servers. I separated the services by their jobs: identity, configuration management, monitoring, remote access, inventory, documentation and automation.

That separation made the environment easier to understand. If the problem concerned a user account, a workstation setup or a network connection, I could work from the relevant service and its documentation rather than treating the whole installation as one unknown system.

The main services I used

FreeIPA / SSSDCentral identity and workstation integration
Ansible / SemaphoreConfiguration and provisioning
ZabbixInfrastructure and workstation monitoring
WireGuardRemote access
NetBox / BookStackInventory and the knowledge base
JenkinsAutomation jobs and CI/CD

I kept a service inventory and an infrastructure map alongside the installation. Those records connected each service with its purpose and the rest of the environment. I needed them for ongoing administration and for someone else to be able to follow the setup.

The two-server setup was a way to use the equipment available and build the infrastructure this business needed for its daily work.

02 / IDENTITY AND USER ENVIRONMENTS

I wanted central administration instead of separate computers.

I used FreeIPA for centralized identity and SSSD to connect the Linux workstations to it. The environment also included a directory replica. This gave me a common way to work with identity and access across the computers.

In December 2025, the workstation environment had 57 Xubuntu 24.04 LTS computers and four Windows endpoints. My infrastructure work was mainly Linux-focused. I also administered Google Workspace for the company.

Centralized home directories

I worked on NFS-based home directories with FreeIPA integration. The aim was to connect the user environment with the central identity setup rather than keep every user’s working environment tied to one independently managed computer.

That rollout was still ongoing. It belonged to the same effort as workstation provisioning: make the computer setup easier to repeat, administer and support as people joined, moved or left.

Network separation and remote access

I worked with network segmentation and WireGuard remote access. The infrastructure needed to support the office computers as well as remote access to the environment. I documented that setup alongside the services, rather than leaving it as something only I knew how to reach.

03 / THE COMPUTER SOMEONE ACTUALLY WORKS ON

A ready workstation includes the headset and the connection.

I handled workstation provisioning, setup, patching and troubleshooting. In a call-centre environment, that also meant checking the equipment people used for calls and the browser-based tools they worked in.

The onboarding checklist included making sure the PC, headset and internet connection were ready at the assigned seat. That sounds simple, but an account can be created correctly while the person still cannot do their work because one of those other parts is missing.

Start with the problem in front of the user.

The quick guides covered browser problems, no sound, slow computers and lost connectivity. They started with practical checks: restart the browser, check the network and USB connections, and restart the computer if needed.

I wrote those steps so the user could do the first checks and report what happened. I still needed to handle the problem, but a report saying which computer was affected and which checks had already been tried was much more useful than only being told that something did not work.

I also handled endpoint protection and access administration. Those tasks were part of keeping the workstation environment usable over time, alongside the server work.

04 / AUTOMATION AND DEVELOPMENT

I could not spend all day running around fixing computers.

My reason for automating was practical. If all my time went into repeating the same installation or maintenance steps, I could not spend it on the infrastructure, the documentation or finding the cause of the next problem.

I developed Bash and Perl scripts for workstation deployment and administration. I used Ansible and Semaphore for configuration management and provisioning, Terraform for infrastructure automation and Jenkins for jobs and CI/CD.

Make the work repeatable.

The scripts and configuration work brought common tasks into a method I could run again. A workstation setup should not depend on remembering every change made to the previous computer. The same applied to maintenance across several machines.

Semaphore provided an interface for the automation tasks. Jenkins had its own place in the jobs and development work. I used those tools alongside scripts, rather than expecting one tool to cover every practical administration task.

How Atomator started

Atomator began as internal Bash work for this workstation environment. It later became a public Linux administration project and an Android companion. The mobile app brought host and group targeting, SSH and maintenance controls to my phone.

I also developed PHP applications using Laravel at Sweet. Development, automation and infrastructure support were connected parts of the role, rather than separate jobs passed between teams.

05 / MONITORING AND TROUBLESHOOTING

I need to know whether it is one computer or the whole office.

I used Zabbix for infrastructure monitoring and workstation agents. Monitoring gave me another way to understand a report, alongside what the user was seeing and the equipment records.

The quick guides made a distinction between one affected computer and several affected computers. If several people lost the same function at once, I needed that information early. The reporting template asked for the approximate number affected and the area of the office.

For a single-computer report, the guide asked for the computer identity, seat, problem and the checks already tried. This connected the human report with the workstation and the infrastructure behind it.

Monitoring and the support action belong together.

A monitoring screen on its own did not finish the job. I still needed to understand what the result meant for the user and decide whether to work on a machine, a connection, a service or the upstream provider.

I also wrote monitoring and IT-policy material. I wanted the intended handling and procedures written down, so the technical setup and the way people were expected to use it could be followed together.

06 / ONBOARDING AND OFFBOARDING

The account has a beginning and an end.

I documented the onboarding steps around a person’s start date, the required business-tool accounts, the right group or role, and the workstation they would use. Google Workspace was part of that process when a company email account was needed.

The process linked IT with the people coordinating the team and the office. A new user needed the right access and a ready workstation, not simply a name added to one system.

Leaving needed a checklist too.

The offboarding instructions covered removing or deactivating access across the relevant systems, checking special permissions and updating the records. Where account data needed to be retained or transferred, that was part of the process.

The checklist ended with verification and communication: the access had been dealt with, the documentation updated and the responsible people informed. I wanted the end of the process to be clear, rather than assume that changing one account completed everything.

07 / DOCUMENTATION AND SUPPORT

Someone else needs to be able to take over.

I wrote the infrastructure map, service inventory, installation instructions, onboarding and offboarding checklists, troubleshooting guides and IT-policy material. I kept English and Swedish user guides so the instructions were useful to the people working there.

BookStack held the knowledge base. NetBox held the network and device records. Those were different kinds of information, but they helped with the same support work: identify the equipment, understand the service and follow the right procedure.

I did not want the documentation to exist only for the original installation. It needed to help with a new employee, a machine problem, an access change or the next person administering the environment.

My daily work also included vendor and internet-provider coordination, maintenance, patching and support. Building the environment and operating it afterwards were connected responsibilities.

08 / WHAT I STARTED EXPLORING

Could I see a connectivity problem earlier?

I had an idea for a self-healing network long before this project. At Sweet I started exploring how AI could help me understand connectivity problems and prepare the computers for them.

I could not replace all the upstream equipment. I could work on the computers and the way they reached services. I experimented with AI-assisted troubleshooting and changes to client DNS settings during connectivity problems.

This was a learning project, not a validated predictive system. It made me more interested in how the existing monitoring, scripts and infrastructure information could be used together. I wanted to get further than reacting to the problem after someone could no longer work.

That interest continues in my software projects. I want to understand what an automated action actually does, what information it used and where a person still needs to make the decision.

I cannot publish all of my work because of NDAs, client confidentiality and other restrictions.
