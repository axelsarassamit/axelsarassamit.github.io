Building infrastructure I could operate and support.

Separate the responsibilities, document the dependencies.

02 / IDENTITY & ENDPOINTS

A common identity layer for a Linux-focused fleet.

FreeIPA provided centralized identity, with workstation integration through SSSD. The retained service map also records a directory replica. This supported a consistent administration model rather than treating each workstation as a completely separate system.

The workstation context

The December 2025 documentation records 57 Xubuntu 24.04 LTS workstations and four Windows endpoints within the 61-computer environment. It describes Chromium as the workstation browser and a cloud dialer as a main business application.

Centralized home directories

The wiki describes NFS-based home directories and FreeIPA integration. It also marks the rollout as ongoing. I therefore treat it as documented implementation work in progress, not evidence that every workstation had completed migration.

Network and remote access

My work included network segmentation and WireGuard remote access. The public account keeps these at the level of responsibilities and technologies, rather than disclosing live addressing, firewall rules, VPN peers or routes.

Keep the role boundary clear

This was a Linux-focused infrastructure role. Google Workspace administration was also part of my work, but Microsoft 365, Entra ID, Windows Server and Jamf belong to other parts of my career.

03 / AUTOMATION & VISIBILITY

Make repeatable work easier to inspect.

Ansible and Semaphore

I used configuration management and provisioning workflows to support workstation setup and ongoing administration. Semaphore gave those automation tasks an interface, while scripts covered practical deployment and maintenance needs.

Atomator grew from the same problem

My workstation automation also led to Atomator: initially internal Bash workflows, later a public Linux administration project with an Android companion. It addresses my fleet workflows; it is not a claim to replace Ansible in every environment.

Jenkins

The service inventory records Jenkins for CI/CD and automation jobs. That establishes its role in the documented environment. The retained summary does not justify inventing a specific pipeline success rate, release frequency or savings figure.

Zabbix and workstation agents

The documentation records a monitoring server and endpoint agents, with infrastructure monitoring and alerts as their purpose. The operational value is connecting a reported problem with a machine, a service and a support action.

NetBox and BookStack

NetBox supplied network/device inventory context, while BookStack provided a place for the knowledge base. Keeping inventory and procedures close to the service map made them useful for fault-finding and handover.

Monitoring has a privacy boundary

I also authored monitoring and IT-policy material. A written policy describes intended controls and handling; it does not, by itself, prove complete telemetry coverage, legal compliance or an independently audited security outcome.

04 / SUPPORT & HANDOVER

The documentation was part of the system.

The retained wiki includes a service inventory, infrastructure map, installation guidance, onboarding and offboarding material, user quick guides, troubleshooting instructions and monitoring/policy explanations. English and Swedish versions helped connect technical administration with the people using the environment.

The quick guides start with straightforward checks and give users a structured way to report a single-computer problem or a wider outage. That reduces the gap between “something is wrong” and a report IT can act on.

My role combined this documentation with daily support, vendor/ISP coordination, patching, access administration and ongoing maintenance. Building the environment and supporting it afterwards were connected responsibilities.

What stays privateThe public portfolio does not contain the wiki itself, access instructions, customer workflows, internal service addresses, host names, user identifiers, network ranges, credentials or raw configuration exports.

A working systems context, with clear limits.

The retained infrastructure map and quick reference corroborate the service stack and the 61-computer/two-host scope. They are self-maintained operational records, not an employer-issued performance assessment.

The supported result is an operating infrastructure with identity, automation, remote access, monitoring, documented procedures and daily administration. I do not attach an unverified uptime figure, zero-data-loss claim, deployment-efficiency percentage or incident-reduction metric to this case.
